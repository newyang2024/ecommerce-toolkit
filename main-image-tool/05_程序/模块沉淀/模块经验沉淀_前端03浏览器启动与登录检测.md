# 模块经验沉淀 前端03 浏览器启动与登录检测

## 1. 模块目标
在桌面应用里实现"启动浏览器"和"重新检测"两个按钮的完整功能：
- 一键启动专用 Edge（调试端口 9223、独立 profile）。
- 通过 CDP 连接真实浏览器，确认连接成功。
- 检测天猫登录态，把浏览器和登录两个状态用状态灯实时反馈到界面。
- 全程在子线程执行，不卡界面，检测完成后通知采集控制标签页。

## 2. 实际产出
- 新增 ui/browser_worker.py：BrowserWorker(QThread)，支持 launch 和 check 两种模式，通过 state 信号（区域、状态、文字）和 done 信号（是否登录、消息）回传。
- main_window.py 接通两个按钮：_start_browser_worker、_on_browser_state、_on_browser_done、closeEvent，检测期间禁用按钮防重复。
- collect_tab.py 增加 refresh_env 方法，记录 browser_ready 和 logged_in。
- start_app.py 最顶部增加 import threading、import asyncio，这是本模块的关键修复。
- 真机验证：launch 模式启动 Edge、CDP 连接、登录检测全链路通过；窗口状态灯正确变绿；命令行 run.py 不受影响。

## 3. 遇到的问题
Playwright 同步 API 在 QThread 子线程里报错：
set_wakeup_fd only works in main thread of the main interpreter
导致 Playwright 无法在子线程启动，浏览器连接和登录检测全部失败。

## 4. 踩过的坑
- 一开始以为是 Playwright 不支持子线程，实际 Playwright 本身支持在普通子线程运行。
- 排查过程中现象时好时坏，不同测试脚本结果不一致，一度以为是偶发竞态，后来发现是脚本是否在主线程提前导入 threading 导致的稳定差异。
- 自动化测试时直接 click 一个处于禁用状态的按钮是无效的，需要直接调用内部方法。
- 本机离屏平台渲染不了文字，界面验证必须用真实平台加定时截图。

## 5. 原本以为 vs 实际发现
- 原本以为：QThread 子线程是标准 Python 线程，threading 模块天然能识别。
- 实际发现：QThread 子线程在 C++ 层创建，没有经过 threading.Thread 启动，threading 模块第一次通过 current_thread 识别它时才创建 _DummyThread。
- 更关键的是：threading 模块如果第一次是在 QThread 子线程里被导入，模块级执行 _main_thread = _MainThread() 时会用当前线程（子线程）的 ident 去登记主线程，导致主线程身份被错误登记到子线程。后续 asyncio 在 Windows 上创建 ProactorEventLoop 时，主线程判断 threading.current_thread() is threading.main_thread() 会错误通过，进而调用只有主线程能用的 signal.set_wakeup_fd，于是报错。
- 结论：threading 和 asyncio 必须在主线程、且在任何 QThread 启动前完成第一次导入。

## 6. 下游引用及后续开发可能影响该模块的风险检点
- 后续模块4的采集线程 collect_worker 同样跑 Playwright，必须保证它也是在 start_app 已经于主线程导入 threading、asyncio 之后才启动，否则会重蹈覆辙。
- 任何新增的后台线程入口文件，都要确认不是该线程第一次导入 threading。
- BrowserWorker 结束时会 browser.close() 断开 CDP，但浏览器窗口保持打开，后续采集线程会重新建立 CDP 连接，这是预期行为，不要误以为需要保持同一个连接。
- 若将来打包成 exe，要确认打包入口在主线程同样提前导入了这两个模块。
