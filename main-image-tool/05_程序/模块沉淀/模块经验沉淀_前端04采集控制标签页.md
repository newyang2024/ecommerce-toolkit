# 模块经验沉淀 前端04 采集控制标签页

## 1. 模块目标
把命令行 Pipeline 完整接到桌面界面的"采集控制"标签页，让用户不碰命令行就能：
- 选择采集范围（全部或前 N 个）和是否断点续跑。
- 一键开始采集，随时优雅停止。
- 实时看到进度条、当前商品、成功/失败/待复核统计。
- 在界面里实时滚动查看完整日志。
全程不卡界面，且不影响命令行入口。

## 2. 实际产出
- 新增 ui/qt_log_handler.py：QtLogHandler，把 logging 日志转成 Qt 信号。
- 新增 ui/collect_worker.py：CollectWorker(QThread)，在子线程跑 Pipeline，注册/移除全局日志 handler，用信号转发进度事件，停止用 requestInterruption。
- 重写 ui/collect_tab.py：采集设置（范围、断点、开始/停止按钮）、进度区（进度条、当前商品、三张统计卡）、实时日志窗口。
- start_app.py 顶部增加 import onnxruntime，修复本模块暴露的 DLL 加载问题。
- 真机验证：前 2 个商品采集成功、0 失败、结果表生成；停止功能验证通过（当前商品结束后优雅停止、进度保存）。

## 3. 遇到的问题
- 真机采集时 OCR 报 onnxruntime DLL 初始化例程失败，商品全部失败。
- 现象时好时坏，不同测试脚本结果不一致，排查一度没有方向。

## 4. 踩过的坑
- 一开始没意识到是 GUI 环境导致，以为是 onnxruntime 安装坏了，反复重装无意义。
- 自动化测试时直接 click 禁用按钮无效，需要直接调用内部方法。
- 日志 handler 必须在采集结束时 remove_global_handler，否则会一直持有界面对象。
- 停止只在商品之间和长休息生效，单个商品处理中不会被打断，这是有意设计，验证时要等当前商品结束。

## 5. 原本以为 vs 实际发现
- 原本以为：onnxruntime 命令行能跑，桌面环境也应该能跑。
- 实际发现：onnxruntime 的原生 DLL 对加载时机敏感，在 QApplication 初始化之后、非标准 QThread 子线程里首次加载会失败。在 QApplication 前、主线程提前 import onnxruntime 即可，已登记 BUG-20261029-017。
- 原本以为进度和日志要写很多胶水代码，实际 Pipeline 在前端模块1已经预留了回调和全局 handler，本模块主要是把信号接到控件。

## 6. 下游引用及后续开发可能影响该模块的风险检点
- 模块5结果表格、模块6复核清单如果要在采集结束后自动刷新，可以监听 collect_tab 的完成状态或 Pipeline 事件，不要在采集进行中频繁读结果文件。
- 任何新增的后台线程都要确认 onnxruntime、threading、asyncio 已在主线程提前导入，否则会重蹈模块3和模块4的坑。
- 全局日志 handler 注册和移除必须成对出现，新增采集入口时要检查 finally 里是否移除。
- 停止后 summary 的 xlsx 是空字符串，下游不要在停止时去打开空结果；正常完成才有 xlsx 路径。
- 打包成 exe 时要确认入口在 QApplication 前同样提前导入这些库。
