# 模块经验沉淀 验证弹窗暂停继续

## 1. 模块目标
采集过程中频繁点击链接可能触发真正的页面验证弹窗（滑块、安全验证、人机验证），需要工具识别后自动停下、不再继续点击，提醒用户手动处理，同时提供暂停和继续能力，处理完能从断点接着跑，不丢进度。

## 2. 实际产出
- 运行控制：新增 core/run_control.py，用两个 threading.Event 分别表示暂停和停止，提供 request_pause、request_resume、request_stop、wait_if_paused 等方法，线程安全，轮询间隔 0.25 秒。
- 弹窗检测：新增 core/captcha_detector.py，先遍历页面框架检查验证组件 iframe，再检查主文档和各框架文字里的验证特征词，命中抛出 CaptchaDetectedError 并带命中依据。
- 规则配置：rules.yaml 增加 captcha 段，含 12 个验证关键词、7 个 iframe 特征，并把访问异常单独列出，真机调整只改配置不改代码。
- 流程改造：Collector 在页面加载后和定位主图后各检查一次验证弹窗，并在关键节点响应暂停；Pipeline 每个商品开头先 wait_if_paused，验证弹窗时先确保暂停、发事件、阻塞等待，恢复后重试当前商品，不占重试次数。
- 前端改造：采集页按钮调整为开始、暂停、继续、停止，按运行和暂停状态切换可用；收到验证事件自动暂停并弹出 QMessageBox 提醒，collect_worker 接入 RunControl。

## 3. 遇到的问题
- 当前环境无法真机复现验证弹窗，检测规则只能基于天猫常用验证组件（baxia、punish）和通用滑块特征设计，需要在第一次真机命中时核对日志里的命中依据。
- 验证弹窗和访问异常容易混在一起，访问异常用户已确认不影响主图，需要在规则和检测里明确区分，只有验证弹窗才暂停。
- 后端发事件和设置暂停存在时序问题，改成后端先 request_pause 再发事件，避免依赖前端响应速度。

## 4. 踩过的坑
- 验证关键词不能放太宽泛的词，比如单独的“验证”“拖动”可能在正常页面出现，要选“请按住滑块”“拖动滑块”这类只在弹窗里出现的强特征，降低误判。
- iframe 命中比文字命中可靠，验证组件通常有独立框架，检测顺序上先查框架再查文字。
- 暂停等待期间也要能响应停止，wait_if_paused 的返回值区分了恢复和停止，不能只做单纯阻塞。

## 5. 原本以为 vs 实际发现
- 原本以为暂停要改造整个循环结构，实际用 threading.Event 加统一的 RunControl 就能覆盖商品之间和商品内部，改动集中在 Pipeline 和 Collector。
- 原本以为验证弹窗检测要写复杂的弹窗元素判断，实际天猫验证组件有明显的 iframe 标记，配合特征词就能较可靠识别，且规则可配置。
- 原本以为停止和暂停是两套机制，实际统一到 RunControl 后，停止只是在暂停事件之外再置一个停止事件，逻辑更清晰。

## 6. 下游引用及后续开发可能影响该模块的风险检点
- 真机首次命中验证弹窗时，若误判或漏判，优先调整 rules.yaml 的 captcha 关键词和 iframe 特征，不要先改代码。
- 后续改 Pipeline 循环或 Collector 处理步骤时，要保留暂停检查点和 ensure_no_captcha 调用，避免验证弹窗再次被忽略。
- 前端按钮状态由 paused 标志统一驱动，新增控制按钮时沿用 _set_running 的状态口径，不要单独写启用逻辑。
- 两个迁移包已同步本次改动并重新打包，后续再改 core、ui、config 时要同步源项目和两个包，保持三处一致。
