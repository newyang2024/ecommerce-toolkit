# 模块经验沉淀：前端01 Pipeline 改造

## 1. 模块目标
在不改动采集核心逻辑的前提下，给现有 Pipeline 增加进度回调、日志实时推送和中途停止能力，让桌面界面能把采集放到子线程跑，实时看到进度，也能优雅停止。同时保证命令行入口完全不受影响。

## 2. 实际产出
- core/logger.py：新增全局附加日志 handler 机制，含 add_global_handler、remove_global_handler，所有 get_logger 创建的日志器（无论何时创建）都会带上注册的 handler。
- core/pipeline.py：构造函数新增 progress_callback、stop_check 两个可选参数；run 主循环在商品之间检查停止、处理前后发事件；长休息改成分段睡，能及时响应停止；停止时保存状态并返回带 stopped 标记的结果。
- 验证脚本：test_fe1.py，验证全局 handler 注册和移除、Pipeline 回调、停止标志、异常兜底，全部通过。
- 命令行回归：run.py --help 正常，参数和用法不变。

## 3. 遇到的问题
- 测试脚本里把全局 print 替换成收集函数后，收集函数内部又调用 print，造成无限递归，最后用 builtins.print 解决。
- 工具捕获 stdout 时，print 输出一度没显示，改成把结果落盘再读，确认是显示层问题，不是逻辑问题。

## 4. 踩过的坑
- 各模块日志器 propagate 都是 False，日志不会传到根日志器，所以不能只在根日志器上加 handler，必须做全局 handler 注册机制。
- 长休息是 45 到 90 秒，如果整段 sleep，停止请求最长要等 90 秒才响应，必须分段睡。
- 回调函数可能抛异常，要在 _emit、_want_stop 里兜底，避免界面回调的错误反过来中断采集。

## 5. 原本以为 vs 实际发现
- 以为要改很多采集代码，实际只在编排层加了回调和标志，collector 和各提取器一行没动。
- 以为日志推送要逐个模块接，实际用一个全局 handler 注册机制就全覆盖了。
- 实际验证时发现停止逻辑要同时考虑商品之间和长休息两种状态，只处理商品之间会有最长 90 秒的卡顿。

## 6. 下游引用及后续开发可能影响该模块的风险检点
- 采集子线程会通过 progress_callback 收到事件，界面回调必须轻量，不能在回调里做耗时操作，否则会拖慢采集。
- 停止只在商品之间和长休息的每一秒生效，单个商品处理过程中不会被打断，这是有意设计，避免半截数据。
- 全局 handler 注册后要记得在采集结束时移除，否则会一直持有界面对象，可能造成重复推送或对象无法释放。
- 停止返回的 summary 里 xlsx 和 review 是空字符串，界面要区分"停止"和"正常完成"，不能在停止时去打开空的结果文件。
- 命令行入口不传新参数，默认行为和改造前完全一致，新旧两条调用路径共用同一份 Pipeline。
