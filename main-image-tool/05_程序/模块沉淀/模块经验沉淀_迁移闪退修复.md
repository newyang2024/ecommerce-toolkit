# 模块经验沉淀 迁移闪退修复（onnxruntime 版本兼容）

## 1. 模块目标
排查迁移包在目标电脑双击启动闪退的问题，定位真实根因并修复，让工具在没有开发环境的电脑上能正常启动，同时沉淀安全软件拦截的兜底处理方法。

## 2. 实际产出
- 诊断工具：diagnose.py 和诊断闪退.bat，按真实启动顺序分步检查系统信息、原生库、界面库、业务依赖、Qt 插件和 QApplication，结果写日志。
- 根因定位：确认目标电脑 CPU 支持 AVX 和 AVX2、VC++ 运行库正常，问题是 onnxruntime 1.23.2 原生组件在该环境初始化失败，属于新版本二进制兼容性问题。
- 修复：onnxruntime 从 1.23.2 降级到 1.19.2，兼容 numpy 2.2.6，真实图片识别 35 个文字块，桌面程序启动正常。
- 配套：requirements 显式固定 onnxruntime==1.19.2，新增《闪退修复与安全软件白名单指引.md》，登记 BUG-20261030-001。
- 重新打包：223.4MB 的 zip，11273 个条目，解压真机验证版本和 OCR 均正常。

## 3. 遇到的问题
- 目标电脑第一次跑诊断报找不到文件，是 diagnose.py 没放到根目录；后来文件名带副本后缀，bat 调用名对不上，重命名后才跑通。
- 候选版本 1.18.1 要求 numpy 小于 2.0，与当前 numpy 2.2.6 冲突，pip 无法安装，只能选 1.19.2。
- 验证脚本最初用精确匹配且路径漏写 capi 层级，误报文件缺失，核对实际条目名后才确认文件都在。

## 4. 踩过的坑
- 诊断脚本不能依赖问题库本身的导入，否则 onnxruntime 一失败，后面 rapidocr 等检查被连带跳过，要按文件路径直接检查。
- 诊断脚本的导入顺序要和真实启动路径一致，原生库先于界面库，顺序反了会制造新的 DLL 冲突误报。
- .NET ZipFile 在 Windows 打包时条目名带根目录前缀且用反斜杠，验证时要按实际条目名匹配，不能想当然用正斜杠。

## 5. 原本以为 vs 实际发现
- 原本以为 DLL 初始化失败多半是 CPU 不支持指令集或缺 VC++ 运行库，实际两项都正常，根因是新版本 onnxruntime 二进制本身的兼容性。
- 原本以为 onnxruntime 只是 rapidocr 的子依赖不用单独管，实际不固定版本会在重建环境时装回有问题的新版本，必须显式锁定。
- 同样的 DLL 初始化报错文字，可能对应完全不同的根因，BUG-017 是加载时机和线程问题，这次是版本兼容问题，不能只看报错文字下结论。

## 6. 下游引用及后续开发可能影响该模块的风险检点
- 后续升级 onnxruntime 要先在干净环境和目标机型上验证，不能直接追最新版，升级后回归导入、OCR 和桌面启动。
- 重建便携环境或重新打包时，以 requirements 固定版本为准，装完核对版本号和实际识别。
- 若目标电脑仍闪退，优先按白名单指引排查安全软件拦截，企业 EDR 可能需要 IT 配合，先确认隔离区有没有文件被拦。
- 诊断脚本和启动脚本要保持导入顺序一致，后续改动 start_app.py 的导入结构时同步更新诊断脚本。

## 7. 待办
- 降级后的新包需要在目标电脑真机验证能否正常启动，本机无法替代。
- 若真机仍闪退，转安全软件方向，查看拦截提示或联系企业 IT 加白名单。
- 3 个双色推断商品仍建议人工确认，属于历史遗留。
