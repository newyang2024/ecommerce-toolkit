# 模块经验沉淀 前端07 联调、冒烟、全量与文档

## 1. 模块目标
把命令行采集能力和桌面界面完整串起来，做冷启动联调、限量真机冒烟和全量真机验证，确认从启动工具、启动浏览器、登录检测、采集、结果刷新到复核展示的全链路可用，最后补齐使用说明和整体沉淀，作为前端收尾。

## 2. 实际产出
- 冷启动联调：应用启动时自动加载已有结果和复核清单，三个标签页切换正常。
- 限量真机冒烟：检测登录后跑 3 个商品，成功 3、失败 0、待复核 1，结果自动刷新。
- 全量真机验证：47 个商品全部成功、0 失败、待复核 13，回填 68 行。
- 结果一致性核对：全量结果与之前确认的交付结果逐字段对比，时间、价格、赠品、保障、红包、其他、状态全部 0 差异，状态分布一致（43 已确定、18 待确认、7 待复核）。
- 新增《工具使用说明.md》，写明启动、操作、输出位置和注意事项。

## 3. 遇到的问题
- 限量冒烟会生成只有几行的结果并更新指针，导致前端显示不完整结果，需要在冒烟后把指针恢复到完整交付文件。
- 全量跑约 18 分钟，中途多次分批长休息，需要分段等待而不是一次阻塞。

## 4. 踩过的坑
- 全量脚本用前台跑会被自动转到后台，要改用后台任务并轮询进度。
- 读取输出文件时个别命令显示超时，但实际写入已完成，要以文件内容为准。

## 5. 原本以为 vs 实际发现
- 原本以为全量验证主要是确认不报错，实际通过逐字段对比才真正证明了前端全量结果和命令行交付结果完全一致。
- 实际发现前端启动时不自动加载结果体验不好，补上后打开就能直接看到上次结果。

## 6. 下游引用及后续开发可能影响该模块的风险检点
- 全量验证证明前端与命令行共用同一 Pipeline，结果可复现，后续改 Pipeline 要同时回归两条入口。
- 活动 30 日 20 点开始后，18 行待确认价格会补全，复核清单条目数会减少，重跑后要重新核对状态分布。
- 以后换机或打包 exe，要确认启动入口在 QApplication 前提前导入 threading、asyncio、onnxruntime，并核对启动脚本里的 Python 路径。
- 链接库更新后要重新全量跑，注意结果文件和指针会随之更新。
